Design systems

Pepperfry

Building a design system for Pepperfry.

Creating a scalable design foundation from an existing product — and using it to build responsive experiences across breakpoints.

My role

Lead Product Designer

Timeline

3 months

Breakpoints

Five

Design systems · Components · Responsive design · Figma architecture · Documentation

The challenge

The challenge wasn't to start from scratch.

Pepperfry already had an established digital experience and a set of existing components. We needed to understand the existing product, identify and structure its visual language, build a reusable design system, and then use that system to create responsive screen designs.

The work also had to happen within a fixed delivery window, while continuing to support development requirements.

What made it complex

Four constraints shaped how the system was built.

01

Existing system

The new system had to build on existing components rather than breaking away from them.

02

Limited time

A fixed three-month delivery window, requiring design-system work and screen design to overlap.

03

More responsive states

The initial plan considered three breakpoints. The actual ecosystem required five.

04

Designing while documenting

Components, specifications and documentation had to evolve alongside actual screen requirements.

Understanding before building

Before creating components, we first studied the existing product.

We went through the website to understand what was already there, so we wouldn't create a theoretical design system that didn't reflect the real product.

Mapping the existing cart flow — coupons, GSTIN, orders and edge states — before deciding what the system needed to cover.

The system had to represent the product — not the other way around.

Establishing the foundation

We structured the system using an atomic design methodology.

This gave the system a hierarchy and made it easier to understand how individual components combine to create complete experiences.

Foundations

We started by organising the fundamentals that everything else would inherit.

Colour

Removed unused colours, reorganised surface and text colours, defined primary, secondary and tertiary text colours, and added semantic colours plus colours for product tags and swatches.

Layout

Grids for 360, 768, 1024, 1280 and 1600, each with defined margins and gutters — a consistent foundation for responsive layouts.

Typography

Added XS, S, XL and XXL sizes, button typography, hyperlink and strikethrough styles, and a reorganised hierarchy.

Typography was expected to stay largely unchanged — a good example of how a system evolves through real design requirements rather than being perfectly defined upfront.

Colour reorganised into semantic tokens; typography collapsed from a flat list of styles into a named scale.

From atoms to components

Turning foundations into reusable components.

The button system, for example, defined primary, secondary, tertiary and text buttons — moving the system beyond visual consistency and towards predictable component behaviour.

Figma architecture

Reducing unnecessary component complexity.

Some components had a very large number of variants. We refactored them by identifying what actually needed to vary, removing unnecessary variants, and keeping meaningful states and properties.

Keep the flexibility the product needs without making the design file unnecessarily complex.

Designing in parallel

Responsive screens had to start before the component library was finished.

Instead of treating the work as strictly sequential, the team overlapped the two tracks — which allowed the system and the screens to inform each other.

The result

Not simply a collection of components.

A more structured design foundation, reusable across the product while staying connected to the actual Pepperfry experience.

Foundations→Components→Patterns→ Screens→Responsive experiences→Documentation
What I learned

A design system isn't a linear exercise.

01

It evolves as real screens expose new requirements.

02

Components, screens, documentation and development requirements influence each other.

03

Responsive design is more than three devices — real products often need more breakpoints.

Without clear anatomy, states, specifications and usage, components are difficult to scale. Good documentation is part of the design system.

The biggest takeaway

A design system isn't just a library of components.

It's a shared language that helps designers make faster, more consistent decisions — while giving developers a clearer foundation to build from.
